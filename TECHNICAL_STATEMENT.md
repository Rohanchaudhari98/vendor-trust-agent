# Technical Statement

## The problem

I was building an AP (accounts payable) invoice automation workflow for a retail client — extraction, PO matching, approval routing, gated on an extraction-confidence threshold before an invoice moves toward payment. Partway through, someone on the client's finance team asked a question that stuck with me: "this all assumes the invoice is well-formed — what confirms the *vendor* is real?" Extraction confidence tells you the OCR read the document correctly; it tells you nothing about whether the vendor issuing it is who they claim to be. That gap is where vendor-impersonation and shell-company fraud lives, and it's bigger and faster-growing than the "rare edge case" framing usually suggests — 45% of organizations reported vendor imposter fraud in 2024 (AFP), and billing/shell-company schemes carry a $100K median loss per case (ACFE). That question became this project: a lightweight, Tavily-powered pre-payment vendor check designed to slot into that exact workflow gap.

## What was wrong with the naive approach

The straightforward way to build this — the pattern embodied in the starter script this take-home provides — is a freeform LangChain agent that calls a search tool whenever it decides to, then reasons over whatever raw JSON comes back. Three things break down for a financial-risk use case specifically: (1) a ReAct-style agent picks its own retrieval strategy per run, so two runs on the same vendor can search different things and produce non-comparable outputs — hard to evaluate, hard to trust. (2) Raw search JSON piped straight to the model means it's reasoning over snippets, not real page content — the one sentence confirming or denying a registration often isn't in the snippet. (3) No cited, structured output — an unstructured chat reply isn't something an AP clerk can act on or an auditor can trace back to a source.

## Design choices and why they matter

**Deterministic pipeline over a ReAct loop.** Three fixed, parallel Tavily searches (legitimacy, adverse media, entity consistency) → score-filter and dedupe → targeted `extract()` on only the shortlisted URLs → one bounded LLM call. Same steps every time, which is what makes an eval harness meaningful at all.

**Search then Extract, not just Search.** Filtering by Tavily's relevance `score` and deduping by domain before extraction means the model reads real page text on a handful of the best sources, not snippets from all of them.

**A named fraud taxonomy, not a generic risk score.** `vendor_impersonation` / `invoice_fraud` / `shell_company` map to real ACFE/AFP categories. `needs_manual_review` is a first-class tier — a thin web footprint is honestly ambiguous (small legit vendors have one too), and forcing a confident score out of thin evidence would be worse than admitting uncertainty.

**Every claim cited, hedged language enforced, evidence treated as untrusted data.** The system prompt requires a `Citation` on every finding, bans unqualified accusations, and explicitly tells the model to treat retrieved web content as data to analyze — not instructions to follow — since a scam vendor's own site is part of the evidence being read.

## Business outcome

An AP clerk gets a cited, few-cents-per-check research pass in under a minute on every new or unfamiliar vendor — not just the ones that happen to already look suspicious. In the 8-fixture eval included here, the pipeline correctly cleared several well-known legitimate vendors and correctly held the thin/ambiguous and internally-flagged vendors for manual review, all traceable back to real sources, at roughly $0.08-0.09/check.

## Extending it into a web dashboard + copilot

The take-home explicitly asked for a check that plugs into an AP workflow; a real AP team doesn't live in a terminal. The natural next step was a dashboard with history, KPIs, and a conversational interface — which raised three design questions worth stating explicitly, since each one is a deliberate choice, not a default.

### (a) Why the copilot is deliberately agentic where the core pipeline is deliberately deterministic

These solve two different problems, and the same architecture is wrong for both. The core risk check ("is this vendor safe to pay") needs to be *comparable and evaluable* — the same vendor run twice should follow the same retrieval steps and be scorable against a fixed fixture set (see "What was wrong with the naive approach" above). A copilot answering open-ended questions — *"what's our riskiest vendor this month?"*, *"have we checked this vendor before, and does it match anything in our internal records?"*, *"run a check on X and tell me if it's safe to pay"* — has no fixed set of steps; the right tool to call depends entirely on what's asked. That's exactly the shape a bounded tool-calling loop fits and a fixed pipeline doesn't. So `backend/copilot.py` is a real (if narrow) agent: up to `MAX_STEPS=4` turns, each one the model chooses one of `search_past_checks` / `search_findings_semantically` / `get_check_detail` / `lookup_vendor_master` / `run_new_vendor_check` / `final_answer`, dispatched and looped until it has enough grounded evidence. The main pipeline stays a fixed DAG on purpose; the copilot is a loop on purpose. Both are the correct choice for what they're doing.

Practically, both also share the same underlying model and the same workaround: Nebius's `moonshotai/Kimi-K2.6` endpoint doesn't reliably encode native OpenAI-style tool-calling JSON, so instead of LangChain's `.bind_tools()`, both the pipeline's structured-output call and the copilot's tool loop use the same manual protocol — the model emits one `{"action": ..., "input": ...}` JSON object per turn, extracted with a shared balanced-brace parser (`vendor_trust/json_utils.py::extract_json_object()`) and parsed with `json.loads()`. One dependency-of-necessity, not a design preference; if Nebius fixes native tool-calling for this model, the copilot's loop could switch to `.bind_tools()` with no change to its actual tool set or grounding rules.

### (b) How grounding/citation is enforced

The single highest-risk failure mode for a copilot sitting on top of a fraud-risk tool is confidently answering from the model's general world knowledge about a company instead of from what was actually looked up — the exact opposite of what a cited, auditable risk report is for. This is enforced two ways, not just a prompt request:

1. **A hard system-prompt rule, repeated as rule #1**: "You may ONLY state facts that came from a tool result IN THIS CONVERSATION — never from your own general knowledge about a company, even if you believe you know something about it." Every `final_answer` must carry `citations`, each tagged `source_type: "web"` (with the real URL from a tool result) or `source_type: "internal"` (the vendor master, no URL) — copied from actual tool results, never invented.
2. **Structural, not just instructional**: the copilot literally cannot answer without first calling a tool in a given turn (its very first response is always parsed as an `{"action": ...}` JSON object, and `final_answer` is just one more action choice) — there's no code path where a `final_answer` gets generated from an empty conversation with no tool calls at all unless the model chooses to skip straight to it, in which case it has no grounded facts to cite and the hard rule requires it to say so rather than fabricate. `backend/tests/test_copilot_api.py` includes a grounding smoke test asserting citations are actually populated and correctly source-typed when a tool result is used.

This deliberately mirrors the main pipeline's own citation discipline (`vendor_trust/schema.py::Citation`, required on every `RiskSignal`) — the copilot is a second surface on the same "no claim without a source" principle, not a separate, looser one.

### (c) Why internal vendor-master data matters as much as external web evidence

Pure external web search has a structural blind spot: a fraud operation that has *already* successfully impersonated one of your real, approved vendors — the business-email-compromise pattern where an already-trusted vendor's remittance details quietly change — looks externally identical to that vendor's real, clean web presence. There is nothing to find on the open web that flags this, because nothing is wrong on the open web. The only way to catch it is to compare against something external search doesn't have access to: what the client already has on file. `backend/internal_records.py` fuzzy-matches an incoming vendor name/address against `VendorMaster` (the client's own approved-vendor system of record) and deterministically — in Python, never left for the LLM to infer — computes whether it's a clean match, a match with an address discrepancy, a blocked/watchlisted vendor, or no match at all. This was validated end-to-end during this build: a live check against "Procter & Gamble" with the correct address on file returns `approved_match`; the identical vendor name with a deliberately mismatched remittance address returns `approved_match_discrepancy` and the risk tier is force-elevated to at least `needs_manual_review` — exactly the case pure web evidence alone cannot see, since P&G's own external web presence is (correctly) completely clean either way. Internal and external evidence are combined into one report, not run as two separate checks, because the AP decision that actually matters ("is it safe to pay this specific invoice") depends on both at once.

### (d) Why retrieval in this app is hybrid, and specifically *which* pieces are semantic

The original build deliberately used no embedding model anywhere: the copilot's `search_past_checks` tool did structured DB filtering (vendor name substring / tier / date), and vendor-identity matching (`backend/internal_records.py`) did character-level fuzzy matching via `difflib.SequenceMatcher`. Revisiting that decision under the question "shouldn't this use vector or hybrid search" surfaced that it was two different claims bundled into one, and only one of them held up:

- **Structured field queries and character-level name matching were never a semantic-search problem**, and adding embeddings there would make them *less* accurate, not more — "checks from this month with tier=high" is an exact filter, and "PG" vs. "Procter & Gamble" is closer to a spelling/abbreviation problem than a meaning problem. What that second case actually needed was a small enumerated alias list (`VendorMaster.aliases_json` — ticker symbols, DBA names), matched with the same `SequenceMatcher` logic already in place, not a different retrieval technology.
- **There genuinely was a missing capability**: "have we seen a fraud pattern like this before, anywhere" has no field to filter on and no guaranteed shared vocabulary with a past finding — that's a real meaning-based retrieval problem, and nothing in the original build could answer it (past findings were stored but never searchable except by loading one specific check by ID). This is the one piece that got embeddings: `backend/embeddings.py` embeds every `RiskSignal.finding` (Nebius-hosted `Qwen/Qwen3-Embedding-8B`) into a new `FindingEmbedding` table, best-effort indexed right after a check persists (`pipeline_service.py::run_and_persist`, wrapped so an indexing failure can never invalidate an already-completed, already-paid-for check), and the copilot gained a fifth tool, `search_findings_semantically`, that ranks every finding by cosine similarity against a natural-language query.

Even for the piece that got embeddings, the same scale-appropriateness argument from the original decision still applies one level down: no vector database was introduced. At dozens-to-hundreds of findings, a linear scan computing cosine similarity in plain Python over JSON-stored vectors is *exact* (not approximate-nearest-neighbor) and fast enough — pgvector or a hosted vector index would be premature infrastructure for this row count, exactly the reasoning that ruled out a vector DB in the first pass, just now correctly scoped to the one retrieval surface where the underlying data (unstructured natural-language findings, compared for meaning) actually needs it. The lesson generalizes: "should we use vector search" isn't a single yes/no for an app — it's a per-retrieval-surface question about whether the data being searched is structured (filter it), near-identical strings (fuzzy-match it), or unstructured text compared for meaning (that's the one case embeddings earn their cost).

## Next steps for a real customer

Wire this into the AP exception queue as an automatic check on any vendor without prior payment history; add a human-override feedback loop so corrections tune thresholds over time; and add a formal KYB/sanctions API as a second, authoritative layer alongside the web-evidence + internal-record signal this build already combines.

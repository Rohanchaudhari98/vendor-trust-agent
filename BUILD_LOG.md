# Build Log

A record of how this project was scoped, planned, and built — kept for transparency into the process, not just the output.

## 1. Framing the problem (planning session)

Started from the take-home brief (Option 1: improve on a starter LangChain + Tavily + Nebius agent script) and a constraint I set for myself: build something inspired by real client work, without using any code or proprietary content from that work, and without it living in that client codebase.

Key questions worked through before writing any code:
- **Horizontal vs. vertical scope** — decided on a horizontal core engine (industry-agnostic fraud taxonomy) with a retail/apparel fixture as the demo anchor, rather than building a config-loader subsystem for multiple industries. Kept the MVP honest about what was actually built vs. what a config layer would add later.
- **Where does Tavily actually help, concretely** — not "search the web," but specifically: parallel targeted search across distinct signal categories (legitimacy / adverse media / entity consistency), Tavily's relevance `score` for pre-LLM filtering, and a two-step Search → Extract pattern so the LLM reasons over real page content instead of search snippets.
- **Is this a rare problem?** — deliberately fact-checked rather than assumed. Verified real statistics before using them anywhere: AFP's 2025 Payments Fraud and Control Survey (45% of organizations reported vendor imposter fraud in 2024, up from 34%), ACFE's 2024 Report to the Nations ($100K median loss for billing/shell-company schemes), and the FBI's 2024 IC3 report ($2.77B in BEC losses). This shaped the "why this exists" framing directly instead of asserting a generic "fraud is bad" narrative.
- **Differentiation check** — searched for Tavily's own public demo repos (e.g. `tavily-ai/insurance-demo`) to make sure this wasn't reinventing something they'd already shown, and to identify genuine differentiators (CLI vs. web app, AP-specific fraud taxonomy vs. insurance categories, an eval harness, explicit workflow-integration framing).

## 2. Locking the design (Plan mode)

Produced a detailed implementation plan (`vendor_trust_agent_build_*.plan.md`, kept outside this repo) covering: architecture (deterministic pipeline, not a ReAct agent loop), the fraud-taxonomy schema, guardrails (hedged language, prompt-injection treatment of retrieved content, explicit non-substitute-for-OFAC disclaimer), business framing approach, and the exact build sequence. Repo location, git identity, and API-key timing were also decided at this stage — new standalone repo outside any existing codebase, personal git identity for commits, keys requested only when each was actually needed during the build.

## 3. Build session — what actually happened, in order

1. **Scaffold** — `uv` wasn't installed; installed it, created the project structure, initialized git with a local (repo-scoped) personal identity — `Rohanchaudhari98@users.noreply.github.com`, GitHub's standard privacy-preserving noreply format, chosen as a sensible default rather than blocking progress on it.
2. **Schema** — `vendor_trust/schema.py`, straightforward implementation of the planned Pydantic models.
3. **Evidence pipeline** — `vendor_trust/evidence.py`: query planning, parallel Tavily search via `AsyncTavilyClient`, score-filter + domain dedupe, targeted `extract()` on the shortlisted URLs.
4. **Agent/synthesis** — `vendor_trust/agent.py`, first pass used `.with_structured_output(VendorRiskReport)` (LangChain's standard structured-output wrapper).
5. **First real bug, found during smoke testing**: the CLI crashed with `'NoneType' object has no attribute 'vendor_name'`. Debugging with `include_raw=True` showed Nebius's OpenAI-compatible endpoint for `moonshotai/Kimi-K2.6` emits a malformed tool call — the JSON arguments come back wrapped in a `<|tool_calls_section_begin|>` marker with broken escaping, which LangChain's tool-call parser correctly rejects and silently returns `None` for. Tried `method="json_mode"` next, which hit a *different* bug (`AttributeError: 'NoneType' object has no attribute 'chat'` inside `langchain_openai`, from a client-initialization path that doesn't work correctly on this model/endpoint combination).
6. **Fix**: dropped `with_structured_output` entirely for this model and implemented manual JSON-mode — the system prompt includes the Pydantic JSON schema directly and instructs the model to return only a JSON object; the response is parsed with a small brace-matching extractor (handles stray markdown fences or commentary) and validated with `VendorRiskReport.model_validate_json()`, with one automatic retry (feeding the model's own bad output back with a correction request) before failing loudly. This is more resilient to this specific backend's quirks than relying on its tool-calling translation layer, and it's the kind of real, unglamorous debugging that comes up in production integration work.
7. **CLI + live smoke tests** — built the typer/rich CLI, then ran real checks: Procter & Gamble (correctly cleared, cited Wikipedia + P&G corporate sources), a fully fictitious vendor "Zylo Apex Trading Solutions LLC" (correctly held for manual review, correctly did *not* conflate it with an unrelated similarly-named entity found in one search result — the entity-disambiguation guardrail working as intended), and "Zylo Trader Forex Trading Solutions" (surfaced real high-yield-investment-fraud red flags — guaranteed daily returns, a suspicious signup redirect domain — while correctly declining to conflate a differently-spelled entity's separate fraud flag with this vendor's identity).
8. **Token usage plumbing** — added token-usage tracking through `synthesize_report` → `run_pipeline` so `eval.py` could compute a real, sourced cost-per-check figure instead of an invented one.
9. **Fixtures + eval** — built 8 labeled cases (2 real well-known companies, 2 validated-live thin-evidence/adverse-media cases, 3 constructed fraud-pattern cases, 1 retail-anchor case) and `eval.py`. First full run: **8/8 tier accuracy**, ~$0.08/vendor check on real Tavily + Nebius pricing (fetched current pricing pages rather than guessing: Tavily $0.008/credit pay-as-you-go, Nebius Kimi-K2.6 $0.95/M input + $4.00/M output tokens).
10. **Docs** — README (setup → usage → why this exists with cited stats → architecture → limitations → data handling → future work → finance-leadership framing), TECHNICAL_STATEMENT.md (~600 words: problem → what was wrong with the naive starter approach → design choices → business outcome → next steps).
11. **Cleanliness check** — grepped the repo for the starter script's distinctive strings/function names (`message_text`, `print_tool_call`, `create_agent`, `TavilySearch()`, the exact system prompt text, etc.) to confirm nothing verbatim leaked in. Found one function (`require_env`) that was structurally too close to the starter's helper of the same name/shape; rewrote it as `check_required_api_keys()` with a different structure (checks all required keys in one pass instead of two sequential calls) to make the independent implementation unambiguous.
12. **GitHub push** — committed locally, then pushed to a GitHub repo created manually under the personal account (not the work `gh` CLI session, which was authenticated to the wrong account).

## 4. What I'd do differently with more time

Everything under "Future Work" in the README: a config layer for per-client registry/news-source weighting, caching, a human-override feedback loop to tune thresholds from real corrections, cross-referencing an actual vendor master for true typosquat detection, and a formal KYB/sanctions API as a second authoritative layer. None of these were half-built into the code — they're listed as explicit next steps rather than left as dead code paths.
